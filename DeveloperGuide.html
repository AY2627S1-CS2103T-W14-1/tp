Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows the general interaction between components when the user issues a command. In CampusContacts, a contact is addressed by its name and, when required, its displayed suffix (for example, delete John Tan_2).

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, StatusBarFooter, HelpWindow, and ContactDetailsWindow. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.
  • opens a ContactDetailsWindow when a successful show command returns a selected contact in its CommandResult.

Event-driven UI interactions

The UI uses JavaFX's event-driven programming model. UI components register event handlers for user interactions, such as button clicks and command submissions. When an event occurs, JavaFX dispatches it to the corresponding handler.

For command execution, the command box's event handler retrieves the entered command and passes it to the Logic component. The resulting CommandResult is then used to update the result display or trigger other UI actions, such as opening a contact details window.

The UI also observes changes to the model's contact list. When the model updates its observable list, the corresponding UI components are refreshed automatically.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.
  • AddCommandParser recognises /role, /email, /phone, and /location, and uses the tokenizer's preamble as the name. It rejects missing fields and duplicate required prefixes, then delegates value validation to ParserUtil. Location maps to the existing Address value object. Optional tags retain t/ (or /tag); edit and find use corresponding slash prefixes. Storage and duplicate-name suffix allocation remain model/storage responsibilities, not parser responsibilities.
  • ShowCommandParser and DeleteCommandParser accept NAME[_NUMBER]. The optional number selects a particular contact from a name bucket; omitting it selects the unsuffixed contact.

Model component

API : Model.java

The Model component,

  • stores address book data in a UniquePersonHashMap. It groups contacts by their base name and stores each group in a TreeMap<Integer, Person>.
  • gives each stored contact a PersonIndex. The first contact in a name bucket has index 0 and is displayed without a suffix; subsequent contacts are displayed with a suffix derived from their 1-based index, such as John Tan_2.
  • keeps an unmodifiable flattened ObservableList<Person> ordered by base name and then bucket index. This preserves a straightforward list for the existing UI and filtered views.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)
  • saves contacts as nested name buckets under personsByName. Each bucket stores a map from the zero-based PersonIndex to the contact data.
  • supports legacy flat persons JSON files when loading. They are converted into buckets in memory and are saved in the new nested form on the next write.

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Contact identity and name-bucket storage

CampusContacts allows several contacts to share the same name. AddressBook owns a UniquePersonHashMap, whose outer TreeMap groups contacts by name. Each group is a PersonNameBucket containing:

  • a TreeMap<Integer, Person> for deterministic ordering by PersonIndex;
  • a priority queue of released indexes, so the smallest available index is reused after a deletion; and
  • the next new index to use when there is no released index.

When an UnindexedPerson is added, UniquePersonHashMap allocates an index and creates the corresponding indexed Person. Removing a contact releases its index. The map then refreshes its flattened observable list so the existing list UI remains in sync.

The storage snapshot is structured as follows:

{
  "personsByName": {
    "John Tan": {
      "persons": {
        "0": { "name": "John Tan", "phone": "90000001" },
        "1": { "name": "John Tan", "phone": "90000002" }
      }
    }
  }
}

On startup, JsonSerializableAddressBook validates each bucket, recreates the indexed Person objects from the nested map keys, and passes the result to AddressBook#setPersonBuckets. The name bucket rebuilds its released-index queue and next-index value once. Normal add, delete, and edit operations use the in-memory map; LogicManager subsequently saves a snapshot through Storage.

Adding contacts and assigning identifiers

Parsing, command execution, and identifier assignment are separate steps. AddCommandParser validates the input and creates an immutable UnindexedPerson; AddCommand passes that value to the model, which is the only component responsible for assigning a PersonIndex.

UniquePersonHashMap finds the contact's name bucket, allocates the smallest available zero-based index, and calls UnindexedPerson#withPersonIndex(...) to create the indexed Person. It inserts that Person into the bucket and refreshes the flattened observable list used by the UI. The temporary unindexed value is not stored after conversion.

Roles, edit history, and sorting

Contacts have one of two normalized roles: student or professor. The model uses the Student and Professor subclasses to hold role-specific fields. Student contacts may have a major and year, while professor contacts may have a faculty, department, and office hours. The parser rejects fields belonging to the other role, so invalid combinations are stopped before they reach the model.

Each stored contact also has createdAt and lastEditedAt timestamps. They are persisted with the contact and are used by sort add and sort edit. The supported sort fields are name, phone, add, and edit. For timestamp fields, ascending order means most recent first. Name sorting uses the PersonIndex as a tie-breaker, which keeps duplicate names deterministic even when the direction is reversed. Legacy contacts without timestamps are given one migration timestamp when loaded.

Exclusive access to the data folder

MainApp acquires a DataFileLock before reading contacts or initializing preferences (which also writes to disk). The lock uses FileChannel.tryLock() on data/campuscontacts.json.lock and remains held until shutdown finishes saving preferences. A second launch using the same folder shows an error and exits without initializing its model or saving preferences. Locking errors also prevent startup; the application does not continue without protection.

The sidecar file stays on disk after exit. Ownership comes from the operating-system lock, not the file's existence, so an unexpected process exit does not require deleting a stale file. Deleting or replacing the sidecar while the app is running would undermine this protection. A small synchronized registry rejects repeat acquisitions in the same JVM before opening another channel, since closing such a channel can release process-level locks on some systems. This protects app instances using the same data folder; it does not prevent external editors or older app versions that do not acquire this lock from changing the JSON file.

Contact photo storage

A contact may have an optional Photo reference. When a photo is supplied to add or edit, LogicManager validates the source and asks StorageManager to copy it into the photos directory beside the data file. The contact stores only the generated relative path, and JsonAdaptedPerson persists that path so the photo can be resolved after a restart. PNG, JPG, JPEG, and GIF files are supported. edit ... /photo [blank] removes a photo.

Photo files are managed separately from the JSON snapshot. After a successful save, StorageManager removes managed photo files that are no longer referenced by any contact. If importing a photo or applying the command fails, the newly copied file is removed so a failed command does not leave an orphaned photo.

Data recovery and save failures

If loading the address-book file fails, the application starts with an empty address book and first preserves the unreadable file in data/backups/ using a timestamped .bak name. This gives the user a copy to inspect or restore instead of silently overwriting the original. A legacy flat persons file is loaded with missing roles migrated to student, then rewritten in the nested personsByName format on the next successful save.

Normal command execution also treats persistence failures explicitly. The command's in-memory change remains applied, but the failed save marks the session as having unsaved changes. The next command retries the save. If the user attempts to exit while changes are still unsaved, the application asks for yes to exit anyway; any other response cancels the exit. Recent-contact history is restored when a save fails, so a failed show does not persist a history change.

Show contact details feature

The show NAME[_NUMBER] command lets users view the complete stored details of a specific contact without changing its profile fields. A successful selection updates the recently viewed history and, when the recent list is active, moves that contact to the front of the displayed list.

  1. AddressBookParser delegates the command text to ShowCommandParser.
  2. ShowCommand looks for the matching name and PersonIndex in the address book.
  3. On success, it returns a CommandResult containing the selected Person.
  4. MainWindow recognises that result and opens ContactDetailsWindow.
  5. The popup displays the contact's display name, ID, role, phone number, email, location, role-specific academic details, tags, creation and edit timestamps, and photo.
  6. If the contact is a Student, major and/or year may also be displayed where available.
  7. If the contact is a Professor, faculty, department and/or office hours may also be displayed where available.

The popup is deliberately a UI concern: the command resolves a model object. LogicManager records a successful selection in the recently viewed history and attempts to save it before returning the result to the UI. If saving fails, the history change is rolled back and a warning is shown, but the selected contact is still returned to the UI and its details window still opens; the save is retried by a later command.

Recently viewed contacts

AddressBook stores up to ten recently viewed contact identifiers, newest first. Each identifier is the contact's existing name and optional suffix. Reopening a contact moves it to the front. Opening an eleventh distinct contact removes the oldest entry. Callers receive an immutable copy of the history.

ShowCommand finds a contact in the address book and returns it in CommandResult. LogicManager then records the visit and saves the address book. If saving throws IOException, including a permission error, it restores the previous history and reports the error. The result still contains the selected contact, so the popup opens even though the history update was not persisted. A failed contact lookup leaves history unchanged.

RecentCommand asks ModelManager to show contacts in history order using the existing FilteredList and SortedList. This does not change the sort preference in UserPrefs. Reopening a contact refreshes an active recent view. list, add or another filter restores the saved sort order. An explicit sort orders the current results normally; recent returns them to history order.

JsonSerializableAddressBook writes a recentContacts array alongside personsByName. A missing or null array loads as empty history. Loading removes missing contacts and repeated identifiers, then keeps the first ten entries. Null entries or an invalid array structure cause a data-loading error. Deleting a contact removes its history entry before the suffix can be reused. Editing a contact preserves its position in history and keeps the recent view active; if its name changes, the history entry is updated to the new display name. Replacing or clearing the address book also replaces the history.

An ordered list is enough for this feature: it avoids visit timestamps, tied visit times and changes to profile constructors. Tests cover the ten-contact limit, repeat visits, duplicate names, filters, sorting, storage, photos, deletion, clear confirmation and failed saves. Manual checks are listed below.

Favourite contacts

SetFavouriteCommand marks or unmarks a contact using the existing NameIndexParser grammar. It searches the whole address book, so users can mark a contact even when it is hidden by a filter. ListFavouritesCommand shows the selected contacts in the user's chosen sort order. The status command checks the previous selection before updating it, so its feedback distinguishes an added or removed favourite from an unchanged selection on repeated commands.

AddressBook stores favourites as a set of display identifiers: a name and its optional suffix. These identifiers are unique because contact names cannot contain underscores. Storing selections separately lets the feature work without changing Person, its subclasses or photo handling. Callers receive an immutable snapshot of the set.

While the favourites view is active, ModelManager refreshes it after a status change or edit. list and add return to the full contact list. AddressBook#setPerson keeps a contact's selection when its identifier changes. Deleting or clearing contacts removes their selections, so a new contact that reuses a suffix starts unmarked.

JsonSerializableAddressBook writes a sorted favouriteContacts array alongside personsByName. A missing or null array loads as an empty set. References to missing contacts are ignored; an invalid array structure or null entry causes a data-loading error. LogicManager saves the selections through the existing address-book save flow.

Tests cover identifier parsing, repeated commands, filtered views, sorting, JSON compatibility, photo preservation, deletion, suffix reuse and clear confirmation. Manual checks are listed below.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete John Tan_2 command to delete the second John Tan in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete John Tan_2 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

The redo command does the opposite — it calls Model#redoAddressBook(), which shifts the currentStatePointer once to the right, pointing to the previously undone state, and restores the address book to that state.

Note: If the currentStatePointer is at index addressBookStateList.size() - 1, pointing to the latest address book state, then there are no undone AddressBook states to restore. The redo command uses Model#canRedoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the redo.

Step 5. The user then decides to execute the command list. Commands that do not modify the address book, such as list, will usually not call Model#commitAddressBook(), Model#undoAddressBook() or Model#redoAddressBook(). Thus, the addressBookStateList remains unchanged.

Step 6. The user executes clear and confirms with yes, which calls Model#commitAddressBook(). Since the currentStatePointer is not pointing at the end of the addressBookStateList, all address book states after the currentStatePointer will be purged. Reason: It no longer makes sense to redo the add David … command. This is the behavior that most modern desktop applications follow.

Design considerations:

Aspect: How undo & redo execute:

  • Alternative 1 (current choice): Saves the entire address book.

    • Pros: Easy to implement.
    • Cons: May have performance issues in terms of memory usage.

  • Alternative 2: Individual command knows how to undo/redo by itself.

    • Pros: Will use less memory (e.g. for delete, just save the person being deleted).
    • Cons: We must ensure that the implementation of each individual command is correct.

Appendix: Requirements

Product scope

Target user profile:

  • is a university student or teaching staff member
  • has a need to find, identify, or contact people within their university community
  • prefers desktop apps over other types of applications
  • can type fast and prefers typing to mouse interactions
  • is reasonably comfortable using CLI apps

Value proposition: CampusContacts helps university students and teaching staff find and identify people they interact with, while being faster than using a typical mouse-driven GUI application.

Use cases

(For all use cases below, the System is CampusContacts and the Actor is the user, unless specified otherwise)

Use case: Add a contact

MSS

  1. User requests to add a contact by providing their name, role, email, phone number, and location.

  2. System adds the contact and displays a success message.

    Use case ends.

Extensions

  • 1a. User provides an invalid argument.

    • 1a1. System shows an error message indicating an argument is not in the correct format.

      Use case ends.

  • 1b. User adds a contact with a name that already exists.

    • 1b1. System assigns the contact an index in that name bucket and displays a suffix when needed to distinguish it.

      Use case ends.

Use case: Edit a contact

MSS

  1. User requests to edit an existing contact by providing its display name and the fields to change.
  2. System validates the supplied fields and updates the contact.
  3. System displays a success message.

Use case ends.

Extensions

  • 1a. The provided name does not match any existing contact.

    • 1a1. System displays an error message.

      Use case ends.

  • 2a. One or more supplied fields are invalid.

    • 2a1. System displays an error message and does not apply the invalid changes.

      Use case ends.

Use case: Add favourite contacts

MSS

  1. User requests to mark an existing contact as a favourite.
  2. System adds the contact to the favourite selection and displays a success message.
  3. User requests to view favourite contacts.
  4. System displays the selected contacts in the user's chosen sort order.

Use case ends.

Extensions

  • 1a. The contact is already a favourite.

    • 1a1. System informs the user that the contact is already a favourite.

      Use case ends.

  • 1b. The contact does not exist.

    • 1b1. System displays an error message.

      Use case ends.

MSS

  1. User requests to unmark an existing contact as a favourite.
  2. System removes the contact from the favourite selection and displays a success message.

Use case ends.

Extensions

    • 1a1. System informs the user that the contact is already not a favourite.

      Use case ends.

  • 1b. The contact does not exist.

    • 1b1. System displays an error message.

Use case: Sort contacts

MSS

  1. User requests to sort the displayed contacts using a supported attribute and direction.

Use case ends.

MSS

  2. System deletes the person and displays a success message.

Non-Functional Requirements

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. Should be able to hold up to 1000 contacts without noticeable sluggishness in performance for typical usage.
  3. Should be able to return and display results within 2 seconds when searching through a contact list of up to 1000 contacts.
  4. Should gracefully handle identical contact names without crashing.
  5. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.

Glossary

  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Teaching staff: Professors, lecturers, teaching assistants, or tutors who interact with students within the university
  • Location: Represents the primary physical location for a contact, symbolizing a home address or residential hostel for students, and an office or cubicle for teaching staff
  • PersonIndex: A zero-based identifier unique within contacts that share the same base name. It is used for storage and to derive a displayed suffix.
  • Name bucket: The group of contacts with the same base name.

Appendix: Instructions for manual testing

Given below are instructions to test the app manually.

Note: These instructions only provide a starting point for testers to work on; testers are expected to do more exploratory testing.

Launch and shutdown

  1. Initial launch

    1. Download the JAR file and copy it into an empty folder.

    2. Double-click the JAR file.
      Expected: The GUI opens with a set of sample contacts. The window size may not be optimal.

  2. Closing CampusContacts and subsequent launches

    1. Close the window.

    2. Double-click the JAR file in the same folder.
      Expected: The GUI opens with all previous contacts saved automatically.

  3. Saving window preferences

    1. Resize the window to an optimal size. Move the window to a different location. Close the window.

    2. Relaunch the app by double-clicking the JAR file.
      Expected: The most recent window size and location are retained.

Adding a person

  1. Adding a student contact

    1. Test case: add David Li /role student /email david@example.com /phone 91234567 /location UTown /major Computer Science /year 2
      Expected: Contact added as a student and displayed in the contact list.

  2. Adding a duplicate-name contact

    1. Test case: add David Li /role student /email davidli2@example.com /phone 81234567 /location PGPR /major Information Systems /year 1
      Expected: Contact added and automatically assigned the suffix David Li_2.

  3. Role-specific field restriction

    1. Test case: add Betsy Crowe /role student /email betsy@example.com /phone 92345678 /location COM2 /faculty Computing
      Expected: Error indicating students cannot have faculty, department, or office hours. No contact added.

Editing a person

  1. Editing contact details

    1. Test case: edit David Li /phone 98887777 /location Kent Ridge Hall
      Expected: Phone number and location updated for the unsuffixed David Li.

  2. Editing a duplicate-name contact

    1. Test case: edit John Tan_2 /phone 98765432
      Expected: Only the second John Tan is updated.

  3. Clearing an optional field

    1. Test case: edit John Tan /major [blank]
      Expected: The contact's major is cleared, while other fields remain unchanged.

  4. Clearing tags

Recently viewed contacts

Use a disposable data folder and add two contacts named John Tan with distinct phone/email values.

  1. Run recent before viewing a profile. The empty-state message should explain show.
  2. Run list, show John Tan, close the popup, show John Tan_2, then close the popup and run recent. Order: John Tan_2, John Tan.
  3. Open John Tan again, close the popup, then run recent. Order: John Tan, John Tan_2, with no duplicate.
  4. Try show Missing Person and recent extra. They should report errors without changing history.
  5. Open nine additional distinct contacts (using list if hidden). recent must show only the latest ten distinct contacts; evicted contacts remain available with list.
  6. Run sort name desc, then recent: latest-first order should return. Run list: your saved name-descending order should return.
  7. Exit normally and restart in the same folder. recent should preserve membership and order.
  8. Delete a viewed contact, add a replacement reusing its suffix, and run recent. The replacement must not inherit history.
  9. Run clear, then no: history remains. Repeat with yes: contacts and history remain empty after restart.

The automated RecentWorkflowTest additionally injects ordinary IO and permission failures during show saves and verifies that neither history nor active recent-view order changes. GUI popup rendering is a separate manual check.
